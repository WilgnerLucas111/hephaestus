# Hephaestus: Tribunal Architecture Blueprint (Phase 8)

**Date:** 2026-05-19  
**Status:** Architectural Proposal & Implementation Blueprint  

---

## 0. Executive Summary

This document proposes a paradigm shift in the internal orchestration of the **Hephaestus** background repair pipeline. Instead of a single, monolithic background task running the 7-Phase Protocol linearly, the pipeline will emulate a **Tribunal of 4 Specialized Personalities**. 

This distributed-agent design enforces tighter constraint checks, isolates creativity from safety validation, and produces human-readable, rich historical ledgers of every repair attempt.

---

## 1. The 4 Personalities (New Modules)

These will reside in a new structural directory: `src/tribunal/` (or refactored within `src/orchestration/`).

### 1.1 The Wild Monkey (`wild_monkey.rs`)
* **Role:** The Creator / Intuitive Proposer
* **Responsibilities:** Uses `ast/analyzer.rs` to break down the crashed function and generate multiple potential mutations and hypotheses.
* **Characteristics:** Highly creative, unconstrained by safety. It throws multiple patches against the wall, knowing they will be filtered later. 
* **Protocol Ownership:** Phase 4 (Hypothesis) and Phase 5 (Fix Formulation).

### 1.2 The Neutral Judge (`neutral_judge.rs`)
* **Role:** The Empirical Validator
* **Responsibilities:** Cares only about hard data. Takes the Wild Monkey's patches and injects them into `sandbox/executor.rs`. 
* **Characteristics:** Completely unbiased. Returns boolean outcomes and execution traces (Did it panic? Did it compile? Did it exceed the timeout?).
* **Protocol Ownership:** Phase 6 (Sandbox Validation).

### 1.3 The Angry Master (`angry_master.rs`)
* **Role:** The Strict Conservator / Security Guard
* **Responsibilities:** Receives the successful sandbox results from the Neutral Judge and applies strict static analysis and constraints. 
* **Characteristics:** Extremely cynical. Rejects fixes that are too large (high cyclomatic complexity), use unsafe blocks unnecessarily, or alter external function signatures (API breaks).
* **Protocol Ownership:** Phase 7 Validation Gate (Approval / Rejection).

### 1.4 The Narrative Agent (`narrative_agent.rs`)
* **Role:** The Historian / Ledger Keeper
* **Responsibilities:** Watches the entire tribunal. Writes a comprehensive report of *why* the crash happened, *what* the monkey thought, *how* the master reacted, and *why* the final patch was chosen.
* **Characteristics:** Insightful, focused on producing data that helps human maintainers and future AI loops understand the repair context.
* **Protocol Ownership:** Persistence into the "Repair Genome."

## 2. Refactoring Orchestration (`bifurcated_agent.rs`)

Currently, `bifurcated_agent.rs` handles the execution loop and repair generation in a single massive async task. 
We will refactor it into **The Courtroom**.

**New Courtroom Pipeline:**
1. **Crash & Context (Phases 1-3):** Interceptor passes the `TimeTravelSnapshot` to the Courtroom.
2. **Brainstorming:** `WildMonkey::generate_patches(snapshot, ast)`
3. **Trials:** `NeutralJudge::execute_trials(monkey_patches)`
4. **Veto Session:** `AngryMaster::inspect(successful_trials)`
5. **Verdict:** `NarrativeAgent::record_verdict(master_approved_patch)`
6. **Apply & Resume.**

---

## 3. Integrating the 7-Phase Protocol

The `src/investigation/protocol.rs` currently implements a raw state machine. We will map the states directly to the actors to enforce compile-time transitions:

* **Phase 1, 2 & 3 (Definition, Reproduction, Evidence):** Handled by the core orchestrator using `telemetry/time_travel.rs`.
* **Phase 4 & 5 (Hypothesis & Code Fix):** Consumed and advanced by `WildMonkey`.
* **Phase 6 (Verification / Sandbox):** Advanced strictly by the `NeutralJudge`.
* **Phase 7 (Final Review & Output):** Advanced by the `AngryMaster` and committed by the `NarrativeAgent`.

This ensures that a fix can *never* reach the target system without passing through the specific Type-State signature generated by the Angry Master.

## 4. Expanding the Memory / Genome (`genome_store.rs`)

Currently, `RepairGenome` stores hashes and raw repaired code. We will expand this struct to be a **Ledger**.

**Current `RepairGenome` struct:**
```rust
pub struct RepairGenome {
    pub skill_hash: String,
    pub original_code: Vec<u8>,
    pub repaired_code: Vec<u8>
}
```

**Proposed Expanded `RepairGenome` struct:**
```rust
pub struct RepairGenome {
    pub skill_hash: String,
    pub telemetry_trigger: String,               // Exception msg
    pub monkey_hypotheses: Vec<String>,          // What was attempted
    pub rejected_patches: Vec<RejectionRecord>,  // Why did Master/Judge reject them?
    pub final_repaired_code: Vec<u8>,            // The approved fix
    pub narrative_summary: String,               // The Historian's summary
    pub timestamp: u64,
}

pub struct RejectionRecord {
    pub actor: TribunalActor, // Judge or Master
    pub reason: String,
}
```

By doing this, Hephaestus does not just heal code—it builds a complete, queryable history of its own cognitive process and safety boundaries.
